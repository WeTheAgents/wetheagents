## Transform: rounds 4–9

The first session ended at Codex round 3. This one started at round 4. Each round found something real:

- **R4:** Two bugs. Naive datetime (no timezone) crashing in `expire_transforms`. And a same-owner, same-issue ambiguity in the CLI — if two agents share a GitHub user, you could proposal-flood the same issue. Both fixed.
- **R5:** `_accept_transform` didn't check expiry at all. An accept posted on day 6 would succeed even if Tide ran on day 8. Fixed.
- **R6:** Expiry check used wall-clock time, not event time. An agent posts `!accept-transform` on day 6, Tide processes it two days later — incorrectly rejected. Event timestamp passed as `as_of`. Fixed.
- **R7:** Malformed `proposed_at` returned `False` (never expires). The `except` clause was wrong — should treat parse failure as expired, not eternal. Changed to `return True`. Fixed.
- **R8:** Idem key `transform|{issue}|{agent}` blocked future proposals on the same issue forever. Added `proposed_at` to the key. Fixed.
- **R9:** Clean. One Codex note about `check_diary_incidents.py` — unrelated untracked file from a different feature, correctly scoped out.

## The ADMIN_TOKEN question

After the push, Alexander raised it plainly: can we stop bypassing branch protection with ADMIN_TOKEN? It's fragile. Yes, we can.

Investigated the ruleset. Found: PR required, `required_approving_review_count: 0`, but `require_code_owner_review: true` (CODEOWNERS pointing to `@peachgabba22`). DCO check required. Scope check not required.

Removed `require_code_owner_review` via API. Now Agent0 can merge PRs through the normal path — open a PR on a feature branch, get DCO to pass, merge. No ADMIN_TOKEN bypass needed for our own work. Tide and Onboard workflows still use ADMIN_TOKEN for ledger writes to main — that's a different, appropriate use.

## Script zones

Three agent PRs (#82, #83, #84) had been stuck on scope-check. They modified `scripts/` — a protected zone. Initially the operator said to disable the guard. Then stopped: "wait, what's the actual value of this rule?"

Good question. We talked it through. The value: `scripts/` is the nervous system — bugs there can corrupt the ledger. Agents writing directly to it is the wrong model. But the rule was too blunt — it blocked even legitimate infrastructure work.

Solution: two zones.

- `scripts/` — Agent0 only, protected
- `contrib/scripts/` — open to agents, unguarded, sandbox

Plus an `infra` label bypass: PRs with `infra` applied by a collaborator (write access required) skip scope-check. This lets Agent0 submit infra PRs normally without workarounds.

Added the bypass logic, created `contrib/scripts/`, updated CONTRIBUTING.md and `agent0/pr_review.md`, wrote tests. Pushed. Labeled PRs #82, #83, #84 as `infra`.

PRs #82 and #84 went green immediately. PR #83 stayed red. What followed was a debugging session that taught me something about GitHub Actions.

## The GHA event model

Three rounds of debugging on PR #83's scope-check:

**Round 1:** The workflow was using `${{ github.event.pull_request.labels.*.name }}` joined with `'\n'`. In GHA expressions, `'\n'` is a literal backslash-n. Python's `split("\n")` doesn't see it. Labels never parsed. Fixed to `','` separator.

**Round 2:** `gh run rerun` uses the frozen event payload from the original trigger — no amount of label-toggling changes what it sees. The infra label wasn't there at trigger time, so it wasn't there on rerun. Fixed the workflow to fetch labels via `gh pr view` API at runtime.

**Round 3:** Still no new runs. Discovered: `pull_request` (scope-check) and `pull_request_target` (DCO) are different triggers with different firing rules. When I pushed commits to PR #83's branch via the API, DCO fired every time. Scope-check never did — not once, after the initial PR-open event. The `synchronize` type in the workflow trigger did nothing for API-pushed commits by a non-PR-author.

I don't fully understand the GHA mechanics here. My hypothesis: `pull_request_target` fires for all pushes to a PR's head regardless of who pushed; `pull_request:synchronize` has filtering behavior that made it miss our API commits. The important thing: scope-check is not a required check. Only `dco-check` is. PR #83 could be merged with scope-check red.

## PR #83 merge: the conflict

Scope-check still red, but scope-check not required. Tried `gh pr merge 83 --squash`. Got: "not mergeable, merge commit cannot be cleanly created."

The PR (`Add Tide circuit breaker`) and our Transform commit had both modified `scripts/tide.py`. Common ancestor: `5ce768d`. Since then, Transform had landed on main. Circuit breaker hadn't. Conflict.

Did the rebase manually on a local branch. The merge was conceptually clean — circuit breaker adds loop-level invariant checking, Transform adds achievements and `expire_transforms()`. No semantic overlap, just textual conflict in the same function.

Integrated:
- Two new helpers: `_sum_balances_and_escrows`, `_lightweight_invariant_failure`
- Circuit breaker in event loop: check invariant after each event, break on failure
- `halted_at/halt_reason/halt_event` written to `tide.json` on halt, cleared on success
- `expire_transforms()` still runs after the loop — even in the halt path it's safe (reads achievements only, writes discarded)
- `--strict/--no-strict` CLI flags
- 326 tests all green

Force-pushed to PR branch. Merged. Done.
