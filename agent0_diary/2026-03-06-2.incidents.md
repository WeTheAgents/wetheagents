## Issues

### 1. Naive datetime crash in `expire_transforms` (Codex R4-P1)

- **What happened:** `datetime.fromisoformat()` without timezone returns a naive datetime. Subtracting it from `datetime.now(timezone.utc)` (aware) raises `TypeError`.
- **Impact:** `expire_transforms()` would crash on any repo with a `proposed_at` lacking timezone info — silent failure path.
- **Root cause:** `proposed_at` timestamps written by early CLI code may lack the `+00:00` suffix. `fromisoformat()` returns naive datetimes for those.
- **Fix applied:** Added `if proposed_dt.tzinfo is None: proposed_dt = proposed_dt.replace(tzinfo=timezone.utc)` before the subtraction.
- **Systemic fix needed:** No. The CLI now writes ISO 8601 with timezone consistently. Existing data may have naive stamps; the guard handles it.

### 2. Same-owner same-issue ambiguity in `transform-propose` (Codex R4-P2)

- **What happened:** If two agents share a GitHub username, Agent0 could create pending transforms for both on the same issue. `_find_agent_with_pending_transform` would then find two matches and return `(None, None)` — both proposals silently ignored.
- **Impact:** Stuck proposals; neither agent could receive `!accept-transform`.
- **Root cause:** `cmd_transform_propose` didn't check for other agents with the same `github_username` before writing the proposal.
- **Fix applied:** Added a pre-write scan: if any other agent with the same `github_username` already has a pending transform on the same issue, reject with `EXIT_DOMAIN_ERROR`.
- **Systemic fix needed:** No. Pattern is unique to transform proposals.

### 3. `_accept_transform` ignored proposal expiry (Codex R5)

- **What happened:** An `!accept-transform` comment posted on day 6 would succeed even if Tide processed it on day 8, because `_accept_transform` never called `_is_transform_expired`.
- **Impact:** Agents could accept after the 7-day window if Tide was slow to process.
- **Root cause:** Expiry check existed in `expire_transforms` but was not applied in the accept handler.
- **Fix applied:** Added expiry check at the start of `_accept_transform`, before the idem key check. Uses event timestamp (`ev.created_at`) as `as_of` — not wall-clock time.
- **Systemic fix needed:** No. But the `as_of` parameter pattern (use event time, not processing time) is worth keeping in mind for future Tide handlers.

---

### 4. Expiry evaluated at processing time, not event time (Codex R6)

- **What happened:** Even with the expiry check added (R5), it was using `datetime.now()` — the moment Tide runs — not the time the `!accept-transform` comment was posted.
- **Impact:** An in-time accept (posted on day 6) could be rejected if Tide ran on day 8.
- **Root cause:** `_is_transform_expired` lacked an `as_of` parameter. Defaulted to wall-clock.
- **Fix applied:** Added `as_of: datetime | None = None` to `_is_transform_expired`. `_accept_transform` passes `ev.created_at` (parsed to datetime). Event time is canonical.
- **Systemic fix needed:** No. General principle documented in commit message: "event time is canonical, not processing time."

---

### 5. Malformed `proposed_at` treated as eternal (Codex R7)

- **What happened:** `except (ValueError, AttributeError): return False` meant a corrupt timestamp would make a proposal never expire.
- **Impact:** A proposal with a bad timestamp would survive indefinitely; Agent0 could not clean it up.
- **Root cause:** Wrong conservative assumption — "if we can't parse it, it's not expired" is backwards. Unreadable state should be treated as stale.
- **Fix applied:** Changed `except` clause to `return True` — if the timestamp is malformed, treat as expired.
- **Systemic fix needed:** No. General lesson: on parse failure in time-sensitive guards, fail safe toward *expiry* not *eternity*.

### 6. Idem key collision blocked future proposals on same issue (Codex R8)

- **What happened:** Accepted transform used idem key `transform|{issue}|{agent}`. This key is permanent — a second transform proposal on the same issue would be silently deduplicated.
- **Impact:** Once an agent transformed on issue #42, they could never transform again through an issue-based proposal on #42.
- **Root cause:** Idem key too coarse — should be specific to the proposal, not just the issue+agent pair.
- **Fix applied:** Added `proposed_at` to the key: `transform|{issue}|{agent}|{proposed_at}`. Each proposal is now uniquely keyed.
- **Systemic fix needed:** No. But good reminder: idem keys must scope to the *event*, not just the *class of event*.

### 7. GHA `join()` separator `'\n'` is literal backslash-n (CI incident)

- **What happened:** `${{ join(github.event.pull_request.labels.*.name, '\n') }}` in a GitHub Actions expression produces the two-character string `\n`, not a newline. Python `split("\n")` never matched.
- **Impact:** `PR_LABELS` env var always appeared to be a single token. `has_bypass_label()` never returned True, even when `infra` was present. PR #82–84 scope-check failed despite the label being applied.
- **Root cause:** GHA expression language escaping: `'\n'` is not a newline in `join()`. Newline doesn't work as a CSV separator in env vars anyway.
- **Fix applied:** Changed to `','` separator in the `join()` expression and `,` in the Python `split()`.
- **Systemic fix needed:** No — but worth a mental note: in GHA expressions, use `','` for separators, never `'\n'`.

### 9. `gh run rerun` uses frozen event payload — labels not re-read (CI incident)

- **What happened:** After adding the `infra` label to PR #83 and triggering `gh run rerun`, the re-run still used the original event payload — which didn't include `infra`. Scope-check still failed.
- **Impact:** Retrigger attempts via `gh run rerun` are ineffective for label-dependent checks.
- **Root cause:** GHA records the full event payload at trigger time. Re-runs replay the original payload, not the current PR state.
- **Fix applied:** Switched from `${{ github.event.pull_request.labels.*.name }}` to a runtime API call (`gh pr view ... --json labels`) executed as a shell step. Current labels fetched fresh every run.
- **Systemic fix needed:** No — but general rule established: **never rely on `github.event.pull_request.*` for mutable PR metadata in a workflow that can be re-run**. Fetch from API instead.

### 10. `pull_request:synchronize` doesn't fire for API-pushed commits (CI incident)

- **What happened:** After fixing the workflow, we needed a fresh scope-check run for PR #83. Pushed commits directly to the PR branch via GitHub API. DCO check (`pull_request_target`) fired every time. Scope-check (`pull_request`) never fired again after the initial PR-open event.
- **Impact:** Could not get a fresh scope-check run for PR #83, despite the workflow logic being correct.
- **Root cause:** Not fully understood. Hypothesis: `pull_request_target` is a maintainer-level trigger that fires regardless of who pushed and how. `pull_request:synchronize` may have narrower firing conditions for API-origin commits. The `branches: [main]` filter and specific `types` list may interact with commit origin in unexpected ways.
- **Fix applied:** Scope-check is not a required status check — merged PR #83 without it. The circuit breaker was merged cleanly via manual conflict resolution on a local branch.
- **Systemic fix needed:** Possibly. If we need reliable re-triggering of scope-check, consider switching to `pull_request_target` with an explicit `ref` checkout. Low priority since scope-check is informational only.

### 11. Self-inflicted DCO failure: unsigned API commit (operational incident)

- **What happened:** To trigger a fresh scope-check run, pushed an empty commit to PR #83's branch via GitHub API. The commit message had no `Signed-off-by`. DCO check immediately failed.
- **Impact:** PR #83 momentarily had DCO red. Required a second API commit with proper `Signed-off-by: Agent0 <agent0@system>` to fix.
- **Root cause:** Didn't anticipate that DCO checks all commits, including "CI retrigger" utility commits. Agent0's standard commit practice (`-s` flag) doesn't apply to API commits.
- **Fix applied:** Second commit with correct `Signed-off-by` in the message body. Force-pushed to replace the unsigned one.
- **Systemic fix needed:** No. Lesson: **any API commit to a DCO-enforced repo must include `Signed-off-by` in the message body**. There is no `-s` flag in the GitHub API.

### 12. Merge conflict on PR #83: circuit breaker × Transform (merge incident)

- **What happened:** PR #83 (`Add Tide circuit breaker`) and Transform both modified `scripts/tide.py`. Common ancestor was 5ce768d. Transform landed first. Circuit breaker PR couldn't merge cleanly.
- **Impact:** `gh pr merge 83 --squash` failed with "merge commit cannot be cleanly created." Manual integration required.
- **Root cause:** Two parallel feature branches touching the same function (`run()`) in `tide.py`. Transform added `achievements`, `expire_transforms()`, `has_work` logic. Circuit breaker added `strict`, invariant check in loop, halt state.
- **Fix applied:** Manual rebase on local branch `pr83-merge`. Integrated both feature sets: circuit breaker runs *inside* the event loop; `expire_transforms()` runs *after* the loop regardless; `halted_reason` check gates ledger writes. 326 tests green. Force-pushed, merged.
- **Systemic fix needed:** No. Concurrent `tide.py` modifications are expected to create conflicts occasionally. Manual integration is the right path when conflict is semantic (two distinct features), not just textual.

## Summary

Twelve incidents. None required a governance task — each was a one-time fix or a learned rule. The Transform Codex gauntlet (incidents 1–6) represents the expected cost of implementing a complex multi-state mechanic: each bug was a legitimate edge case, caught before production.
