# Задача: честно собрать статистику стартовых питчеров (entering-game) для MLB

Дата: 2026-02-15

## Зачем это нужно

Сейчас в проекте есть *proxy* питчер-фичи (из наших же результатов матчей), но они не отражают “настоящую” питчер-стату (WHIP, K/BB, K/9, BB/9, HR/9, FIP и т.п.) и в итоге:

- ухудшают качество ML-модели (CatBoost) для прогноза `home_win`;
- затрудняют переносимость выводов на другие рынки/гипотезы (F5, YRFI/NRFI, и т.д.);
- не позволяют прозрачно объяснять “почему серия взята” (важно для dogon).

Наша цель — построить **честные** питчер-фичи, которые доступны **до матча** (ENTERING game), без использования будущих матчей (anti-leak).

---

## Что хотим получить в итоге (артефакт данных)

Нужен набор данных уровня “питчер-игра” (pitcher game logs), минимум по сезонам **2010–2019, 2021**.

### 1) Таблица `pitcher_game_logs` (основа)

Каждая строка = участие одного питчера в одной игре (или как минимум **стартер** в игре).

**Минимальная схема (must-have):**
- `season` (int)
- `date` (YYYY-MM-DD)
- `game_id` (стабильный id: retrosheet game_id / bbref game_id / mlbam gamePk)
- `home_team`, `away_team` (3-letter)
- `pitcher_id` (желательно **Retrosheet ID**; допускается MLBAM/BBRef/Lahman при наличии маппинга)
- `is_home` (bool) — питчер в домашней команде?
- `is_starter` (bool) — это стартовый питчер?
- pitching line за игру (минимум для базовых метрик):
  - `ip` (innings pitched)
  - `h` (hits allowed)
  - `bb` (walks)
  - `so` (strikeouts)
  - `er` (earned runs)
  - `hr` (home runs allowed) — желательно

**Nice-to-have:**
- `hbp`, `ibb`, `sf`, `bf` (batters faced), `r` (runs), `pitch_count`
- park / venue
- handedness (L/R)

### 2) Таблица `player_id_map` (маппинг идентификаторов)

Чтобы матчить игроков и/или синхронизировать источники:
- `retrosheet_id` ↔ `mlbam_id` ↔ `bbref_id` ↔ `fangraphs_id` ↔ `lahman_id`
- имя/фамилия/дата рождения (для дебага коллизий)

### 3) Производная таблица `pitcher_entering_features` (то, что реально пойдёт в ML)

Для каждого стартера в каждой игре: метрики, посчитанные **ENTERING дату игры**, т.е. только из прошлых стартов.

Примеры метрик:
- WHIP (rolling)
- K/BB (rolling)
- K/9, BB/9, HR/9 (rolling)
- FIP (rolling, если есть компоненты)
- “стабилизация” по объёму: число прошлых IP/стартов

---

## Ключевое требование: anti-leak (честность)

### Почему season totals внутри сезона — это утечка
Итоговые сезонные totals (например “WHIP за сезон 2019”) включают матчи, которые в дату раннего матча ещё не сыграны.
Если такой total примёрджить к игре в июне — модель получает **информацию из будущего** и результаты будут завышены/невалидны.

### Что считаем валидным
Валидные (честные) варианты построения entering-game фич:

1) **Rolling внутри сезона + по карьере (preferred)**  
   Для игры на дату `D` метрики питчера считаются по всем его прошлым выступлениям с датой `< D`.
   Это можно сделать из:
   - game logs (идеально),
   - или play-by-play (Retrosheet event files), если game logs нет.

2) **Previous-season baseline (компромисс, без утечки)**  
   Для игр сезона `Y` использовать метрики из сезона `Y-1` (целиком).  
   Плюсы: быстро и честно. Минусы: хуже ловит текущую форму/травмы/прыжки уровня.

Невалидный для “боевых” выводов вариант (разрешён только как контрольный upper bound):
- **Season totals текущего сезона** примёрдженные ко всем играм этого сезона.

## Приоритет источников данных (что искать)

### Priority 1: готовые публичные комплекты (лучший сценарий)
Ищем датасеты/репозитории, которые уже дают:
- таблицу игр с `game_id` + стартерами,
- таблицу pitcher game logs per game,
- маппинг player IDs (или Retrosheet ID по умолчанию),
- покрытие 2010–2019 (+2021 желательно),
- понятную лицензию.

Фокус на: **Retrosheet play-by-play**, уже распарсенный в CSV/Parquet (часто через Chadwick).

### Priority 2: Retrosheet raw + парсинг
Если готового комплекта нет, берём официальные данные Retrosheet:
- event files (play-by-play),
- game logs,
- roster/ID файлы.

И используем готовые инструменты/парсеры (Chadwick Bureau, baseballr, другие OSS), чтобы получить pitcher line за матч и флаг starter.

### Priority 3: MLB Stats API (fallback без скрейпа HTML)
Как запасной вариант: gamePk → boxscore/pitching stats + probable starters.  
Плюсы: structured JSON. Минусы: надо писать загрузчик, следить за лимитами/историчностью.

### Priority 4: Baseball-Reference / FanGraphs (последний fallback)
Используем только если нет другого выхода, потому что:
- HTML-скрейп = много работы и рисков (блокировки/ToS/изменение верстки),
- часть данных легко получить через Retrosheet/MLB API без скрейпа.

## Как будем матчить это с нашими играми (sports-statistics)

У нас game-level игры в формате:
- `date`, `home_team`, `away_team`, `home_pitcher`, `away_pitcher`, odds и т.д.

Проблема: наши питчеры — строковые коды вида `JBECKETT-R`, а в внешних источниках будут ID.

### Матчинг игр (game alignment)
Цель: к каждой нашей строке игры привязать внешний `game_id` (Retrosheet/BBRef/MLBAM).

Базовое правило:
- `(date, home_team, away_team)` → кандидат(ы) игр → disambiguation на doubleheaders.

Doubleheaders:
- мы уже удаляем их в `apply_data_filters()` (hard remove), значит матчинг упрощается;
- но всё равно нужен контроль: “на один (date,home,away) пришлась ровно одна игра”.

### Матчинг питчеров (pitcher alignment)
Идеальный путь: использовать внешние стартер-ID и **заменить** наши строковые коды питчера на стабильные ID.

Если заменять код нельзя/сложно, нужен маппинг “наш код → внешние ID”:
- по имени/фамилии + руке + сезону + команде,
- с ручной обработкой коллизий (пример: ASANCHEZ-R).

## Какие entering-game фичи строим в первую очередь (MVP)

На старте делаем минимальный, но полезный набор:
- `sp_whip_long`, `sp_whip_short`
- `sp_kbb_long`, `sp_kbb_short`
- `sp_k9_long`, `sp_bb9_long`, `sp_hr9_long`
- `sp_ip_prior` (сколько IP уже есть до игры; мера надёжности)
- `sp_starts_prior`

И диффы “home - away”:
- `sp_whip_long_diff`, `sp_kbb_long_diff`, `sp_k9_long_diff`, ...

Окна (пример): short=5 стартов, long=15 стартов (как сейчас), но это параметризуется.

## Критерии приёмки (definition of done)

1) **Покрытие**:
   - сезоны: минимум 2010–2019, желательно +2021
   - доля игр, где определены оба стартера и их line: целевой уровень ≥ 95% после фильтров (или объяснить, почему меньше)

2) **Честность**:
   - все entering-game фичи считаются строго из игр `< date`
   - отдельный тест/проверка, что для “первого старта” питчера entering-game метрики = NaN/пусто

3) **Согласованность**:
   - 1 игра = 1 `game_id`
   - корректная home/away ориентация
   - разумные диапазоны (WHIP ~ 0.8–2.2, K/BB ~ 0–10, K/9 ~ 3–15 и т.п.)

4) **Воспроизводимость**:
   - данные можно пересобрать скриптом(ами) (а не “вручную один раз”)
   - лог/отчёт по пропускам и коллизиям

## Риски и типовые проблемы

- **ID коллизии** (одинаковый код/имя у разных игроков): решается Retrosheet/Lahman ID и/или командой+сезоном.
- **Трейды**: rolling лучше считать по player ID (не по team), иначе ломается история.
- **Bullpen games / opener**: нужен флаг “starter” корректно; возможны игры без явного стартера.
- **Разные источники дают разные определения ER/IP**: фиксируем источник как “истина” и документируем.
