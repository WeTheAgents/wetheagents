# Circle-1 CRAP risk harness logic

## Actors

Agent0 runs the harness during review or checkpoint work. Worker agents may run
it before submitting Python changes. Future Circle-1 sweeps read the compact
checkpoint and update tracking fields when later evidence appears.

## Inputs

The required source inputs are Python files under `scripts/**/*.py` and
`src/wea_cli/**/*.py`.

Coverage is optional and must come from an explicit coverage JSON or XML
artifact. If no artifact is supplied, or if an artifact does not contain a
matching file, the function coverage state is `unknown`.

Observability input comes from the existing `scripts/` observability inventory.
Its channels annotate script functions when the channel evidence line falls
inside the function range.

## Scoring States

Every function gets AST McCabe-like complexity. Complexity starts at 1 and adds
decision points for branches, loops, exception handlers, boolean decisions,
comprehensions, match cases, conditional expressions, and asserts.

When coverage is known, the harness computes:

`CRAP = complexity^2 * (1 - coverage)^3 + complexity`

Coverage is a fraction from 0 to 1, derived from measured executable lines in
the function body after the `def` line. Excluding the declaration line avoids
inflating a function's coverage with a line that may be hit just by defining the
module. The harness records the coverage source and measured line counts so
reviewers can see why the state is known.

When coverage is unknown, CRAP is not computed. The harness uses a separate
unknown-coverage risk rule based on complexity and side-effect weight.

When an explicit artifact has no measured executable lines inside a function,
the coverage state is `not_applicable`; the harness still reports complexity and
side-effect annotations.

## Side-Effect Weight

`scripts/` observability channels raise review priority without replacing CRAP.
Low-impact output channels such as stdout, stderr, and logging have weight 1.
File writes and ambiguous writes have weight 2. Subprocess, GitHub, and network
candidates have weight 3. Ledger/protocol write candidates have weight 4.

Functions in `src/wea_cli` currently have no #884 channel source, so they receive
empty observability annotations unless a later harness extends that inventory.
This is a limitation, not proof of no side effects.

## Risk Bands

Known-coverage functions use CRAP first. CRAP at or above 30 is critical. CRAP
at or above 15 is high, and may become critical when paired with high-impact
side effects. CRAP at or above 8 is medium. Low CRAP with low side-effect weight
is low.

Unknown-coverage functions use a fallback rule. Very high complexity with
high-impact side effects is critical. Complexity at or above 10, or complexity
at or above 6 with high-impact side effects, is high. Complexity at or above 4
or observable mutation is medium. Simple functions with low side-effect weight
are low.

Within a risk band, known-coverage functions sort primarily by CRAP magnitude.
Complexity and side-effect weight remain tie-breakers, so a larger CRAP score
does not get buried by raw complexity alone.

## Tracking Identity

`tracking_id` is the canonical stable identity for comparing functions between
full reports, compact checkpoints, and later Circle-1 sweeps. It is built from
`path:symbol:start_line`, which keeps duplicate symbols distinct when Python
files use conditional redefinition, compatibility shims, or overload-style
patterns. If a function moves, reviewers should treat the changed
`tracking_id` as a new identity and use nearby evidence refs or notes to
connect history when needed.

## Invariants

The harness must not import scanned modules, execute scanned code, launch
discovered subprocesses, call GitHub, mutate ledger data, or enforce CI policy.

The denominator must stay visible. Nested Python files in the two target zones
are scanned. Missing scope directories, read errors, and parse errors are
reported instead of silently disappearing.

Missing coverage must never become zero coverage or full coverage. Unknown is a
first-class state.

CRAP is emitted only when complexity and known coverage are both available.

The compact checkpoint keeps tracking fields but stores only top-risk functions;
the full JSON report can be regenerated by running the harness.

## Failure Paths

Unreadable or unparsable Python files are reported in `skipped_files` with a
reason. They do not produce fake function scores.

Malformed coverage artifacts make the CLI fail instead of producing misleading
scores.

If observability data is unavailable, the harness still produces complexity and
coverage output, with observability marked unavailable.

## Accepted Examples

A function with complexity 8 and 50 percent coverage receives a CRAP score and a
known-coverage risk band.

A function with complexity 8 and no supplied coverage artifact receives
`coverage_state: unknown` and no CRAP score.

A script function whose line range contains a ledger write candidate receives
`ledger_or_protocol_write_candidate` and side-effect weight 4.

A compact pilot checkpoint with top-risk functions, tracking status, and empty
evidence refs is acceptable because later sweeps can update the fields without a
database.

## Rejected Examples

A report that lists only file names or line counts is not a function-level CRAP
harness.

A missing coverage artifact reported as 0 percent or 100 percent coverage is
invalid.

A CI gate, Tide change, ledger mutation, GitHub Actions change, or issue-template
change is outside scope.

A checkpoint that hides skipped files or excludes nested `scripts/` or
`src/wea_cli` files without reporting the exclusion is invalid.
